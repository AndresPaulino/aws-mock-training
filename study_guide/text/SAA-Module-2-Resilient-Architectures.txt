1. Resilience Concepts: The Vocabulary That Decides Answers

1.1 High availability vs fault tolerance

High availability (HA) means the system keeps working with minimal downtime when a component fails -- there may be
a brief interruption while failover happens (RDS Multi-AZ takes ~60­120 seconds). Fault tolerance is stricter: users notice
NOTHING because redundant capacity is already serving traffic (an ASG across 3 AZs behind an ALB -- lose an AZ, the
other two just keep answering). Fault tolerance costs more because you pay for the redundancy continuously. When a
question distinguishes the two, it's testing whether you'll pay for standby-that-serves vs standby-that-waits.

1.2 Vertical vs horizontal scaling, and why statelessness matters

Vertical scaling = a bigger instance. Simple, but has a ceiling, requires downtime to resize, and the single machine is still
a single point of failure. Horizontal scaling = more instances. Near-limitless and inherently HA -- but only if any instance
can serve any request. That requires the app to be stateless: no user session data, uploaded files, or local caches living
on one box.

CORE CONCEPT -- Externalizing state: The recurring fix pattern: sessions  ElastiCache or DynamoDB; uploaded
files  S3 (or EFS if the app truly needs a shared POSIX filesystem); logs  CloudWatch/Kinesis. Any question where
'users lose their session when an instance is replaced' or 'uploads are missing on some servers' is asking you to move
that state off the instance.

1.3 RPO and RTO

RPO (Recovery Point Objective): how much DATA you can afford to lose, measured backward in time from the disaster
('RPO 1 hour'  backups/replication at least hourly). RTO (Recovery Time Objective): how long you can afford to be
DOWN. These two numbers, plus budget, select the DR strategy (Section 8). Train yourself to extract them from every
scenario -- they're usually stated explicitly.

1.4 Loose coupling

Tightly coupled systems call each other directly and synchronously -- if the downstream is slow or dead, the upstream
fails too, and a traffic spike crushes everything at once. Loose coupling inserts a buffer (queue, topic, event bus)
between components so each side scales and fails independently. This one idea generates most of Domain 2's questions:
web tier drops work into SQS; workers consume at their own pace; a worker crash loses nothing because the message
becomes visible again.

2. Elastic Load Balancing In Depth

2.1 What a load balancer actually does

An ELB is a managed fleet of traffic distributors deployed across the AZs you choose. Clients connect to the ELB's DNS
name; it forwards to healthy registered targets in target groups (instances, IPs, Lambda, containers). Health checks
probe each target; failures pull a target out of rotation. This gives you the fault-tolerant front door: an AZ dies, the ELB
simply stops sending traffic there.

3. Auto Scaling Mechanics

3.1 The moving parts

An Auto Scaling group maintains between min and max instances, targeting desired capacity, spread across the
subnets/AZs you list. A launch template tells it what to launch (AMI, instance type(s), SG, role, user data -- templates
are versioned and support mixed instance types + Spot; legacy 'launch configurations' are immutable and deprecated).
The ASG continuously: (1) replaces instances that fail health checks -- self-healing; (2) rebalances across AZs; (3)
executes scaling policies.

 · Health checks: EC2 status checks by default; turn on ELB health checks so an instance whose APP is dead (but VM
    is fine) also gets replaced -- a favorite exam nuance.

4. Decoupling: Queues, Topics, Events, Workflows

4.1 SQS -- the buffer

A producer writes a message; it's stored redundantly across AZs; a consumer POLLS, receives it, and the message
becomes invisible for the visibility timeout (default 30s). If the consumer finishes, it DELETES the message; if it crashes,
the timeout expires and the message reappears for another consumer -- that's the durability model, and it implies
at-least-once delivery: design consumers to be idempotent (safe to process twice).

 · Standard queues: unlimited throughput, best-effort ordering, occasional duplicates. FIFO queues (name ends .fifo):
    strict order within a MessageGroupId and exactly-once processing, at 300 msg/s (3,000 batched; more in
    high-throughput mode).

 · Long polling (WaitTimeSeconds up to 20): the receive call waits for messages instead of returning empty -- fewer
    API calls, lower cost, lower latency. Almost always 'enable long polling' when SQS cost/empty-receives appear.

 · Dead-letter queue (DLQ): after maxReceiveCount failed attempts, the message moves to a side queue for inspection
    -- poison messages stop clogging the pipeline. Retention up to 14 days (default 4). Max size 256 KB -- for bigger
    payloads store in S3 and enqueue the pointer.

4.2 SNS -- the megaphone

Pub/sub PUSH: publishers send to a topic; SNS immediately pushes copies to every subscriber (SQS, Lambda, HTTP,
email, SMS, mobile push). SNS stores nothing after delivery -- so the canonical fan-out pattern pairs it with SQS: one
'OrderPlaced' event  topic  three queues (billing, shipping, analytics), each processed independently, durably, at its
own pace. Filter policies let each subscription receive only matching messages (e.g., only orders > $100).

4.3 EventBridge -- the router

A serverless event bus. Sources: nearly every AWS service, your apps, and SaaS partners. Rules pattern-match events'
JSON and route to 20+ target types (Lambda, Step Functions, SQS, ECS tasks, another bus in another account...). Also
does cron schedules, event archive & replay, and a schema registry. Default answer for 'when X happens in service A,
trigger B' and cross-account event routing. SNS = high-fanout push to subscribers; EventBridge = content-based routing
between services.

4.4 Step Functions & the rest

 · Step Functions: serverless state machines orchestrating multi-step workflows -- sequences, parallel branches,
    choices, and crucially built-in RETRY and error handling per step. 'Coordinate multiple Lambda functions with
    retries/human approval'  Step Functions, not Lambda-calling-Lambda. Standard workflows run up to 1 year; Express
    for high-volume short bursts.

 · Amazon MQ: managed ActiveMQ/RabbitMQ. ONLY correct when migrating an app already speaking
    AMQP/MQTT/JMS/STOMP that can't be rewritten. New cloud-native designs  SQS/SNS.

EXAM TIP: Buffer & smooth spikes  SQS. One event, many independent consumers  SNSSQS fan-out. React to
AWS service events / route by content / schedule  EventBridge. Multi-step logic with retries  Step Functions. Legacy
broker protocols  Amazon MQ.

5. Route 53: DNS as a Resilience Tool

5.1 DNS in one paragraph

DNS translates names to IPs. Route 53 hosts your domain's records in a hosted zone -- public (answers the internet) or
private (answers only inside associated VPCs). Records: A (nameIPv4), AAAA (IPv6), CNAME (nameanother name;
NOT allowed at the zone apex like example.com). Alias records are Route 53's special type: they point at AWS
resources (ALB, CloudFront, S3 website, API Gateway), work at the apex, are free to query, and track the target's IP
changes automatically -- prefer Alias over CNAME for AWS targets every time.

6.2 Aurora -- what makes it different

Aurora (MySQL/PostgreSQL-compatible) separates compute from a shared storage layer that keeps 6 copies of every
block across 3 AZs (writes need 4/6 -- survives an entire AZ + one more copy failing) and auto-grows to 128 TB.
Because replicas read the SAME shared storage, up to 15 replicas run with ~10ms lag, and failover promotes one in <30
s. Apps use the writer endpoint and the load-balanced reader endpoint.

 · Aurora Global Database: storage-level replication to up to 5 secondary Regions at ~1 s lag  RPO ~1 s, RTO <1
    min. THE answer for aggressive cross-Region relational DR/reads.

 · Aurora Serverless v2: capacity scales in fine increments with load -- variable, spiky, or dev/test workloads without
    capacity planning.

6.3 DynamoDB and ElastiCache resilience

 · DynamoDB replicates across 3 AZs automatically -- Multi-AZ is free and built in. Global Tables = multi-Region
    ACTIVE-ACTIVE (read AND write in every Region, last-writer-wins conflicts). Point-in-time recovery restores to any
    second in 35 days.

 · ElastiCache Redis: primary + replicas, Multi-AZ automatic failover, snapshots. Memcached: no replication, no
    persistence -- a cache you can afford to lose. 'Cache must survive node failure'  Redis.

 · RDS Proxy: managed connection pool in front of RDS/Aurora -- absorbs Lambda connection storms and cuts failover
    time (~66%) by holding connections through it. 'Lambda exhausts DB connections'  RDS Proxy.

7. Backups & Snapshots

 · EBS snapshots: incremental, stored in S3, copyable cross-Region/account -- the building block of instance-level DR.
    AMIs = bootable snapshots; golden AMIs speed recovery and scale-out.

 · RDS/Aurora: automated backups (transaction logs every 5 min  point-in-time restore within retention, max 35 days)
    vs manual snapshots (kept until you delete; survive instance deletion; shareable cross-account). Restores always
    create a NEW instance/endpoint.

 · AWS Backup: one policy-driven service covering EBS, RDS/Aurora, DynamoDB, EFS, FSx, S3, Storage Gateway...:
    schedules, retention, lifecycle to cold storage, CROSS-REGION and CROSS-ACCOUNT copies, and Vault Lock --
    WORM-immutable backups nobody (including root) can delete. 'Centralize backups across services/accounts' or
    'ransomware-proof backups'  AWS Backup (+ Vault Lock).

9. Reference Architecture: Resilient Order-Processing System

Flow: Users  Route 53  ALB (3 AZs)  web ASG (private subnets, target tracking on requests/target)  SNS topic
'OrderPlaced'  three SQS queues (payments FIFO, fulfillment, analytics)  worker ASGs scaling on
backlog-per-instance  Aurora Multi-AZ (writer + 2 readers) + DynamoDB session/cart table. DLQs on every queue; Step
Functions orchestrates payment retries; AWS Backup handles snapshots; Aurora Global Database replicates to a second
Region where a pilot-light copy waits behind a Route 53 failover record.

 · Why each piece: ALB+ASG across 3 AZs = fault-tolerant web tier. SNSSQS fan-out = one event, three independent
    consumers; a fulfillment outage can't lose orders (queue absorbs). FIFO for payments = no duplicate charges, ordered
    per customer. Backlog-based scaling = workers sized by actual work. Aurora readers = reports don't touch the writer.
    Failover record + Global DB = Region-level DR with ~1 s RPO.

Exam questions describe a broken version of this: synchronous webworker calls that drop orders at peak (add SQS),
one NAT/one AZ (add per-AZ), reports slowing production (read replica), no DLQ (poison messages loop forever).

10. Worked Practice Questions

Practice Q1. During flash sales, a web app writes orders directly to RDS. Spikes overwhelm the database and orders are
lost. Users must receive immediate confirmation. What's the best fix?

   # Bigger RDS instance -- vertical scaling just raises the ceiling; spikes will find it again, and it costs 24/7.
   # Aurora migration alone -- faster DB, same tight coupling; extreme spikes still overwhelm synchronous writes.
    Put SQS between the web tier and a worker fleet: confirm the order once the message is queued, let workers write to
   the DB at a sustainable rate, scale workers on queue depth. Queue-as-shock-absorber is the signature Domain 2 answer.

Practice Q2. An application must process payment messages exactly once and in the order each customer submitted
them. Which service?

   # SQS Standard -- at-least-once + best-effort ordering: duplicates and reordering possible.
   # SNS -- push fan-out, no ordering/consumption semantics for a single worker pipeline.
    SQS FIFO with MessageGroupId = customer ID -- exactly-once processing, strict per-group ordering, and different
   customers still process in parallel.

Practice Q3. A company needs RPO of 1 second and RTO under 1 minute for its MySQL database across Regions.
Which solution meets this?

   # Cross-Region RDS read replica -- async lag can be seconds­minutes; promotion is manual and slower than 1 minute in
   practice.
   # Nightly snapshots copied cross-Region -- RPO up to 24 hours.

    Aurora Global Database -- storage-level replication ~1 s lag, secondary promotion <1 min. Those two numbers ARE
   the Aurora Global Database spec; recognize them instantly.

Practice Q4. A reporting team's heavy analytical queries are degrading a production RDS PostgreSQL database.
Least-disruptive fix?

   # Multi-AZ -- the standby is not readable; Multi-AZ addresses availability, not read load.
   # Second RDS instance with manual dumps -- stale data and operational toil.
    Create a read replica and point reporting at it -- async replication offloads reads; production writes untouched. Multi-AZ
   = availability; replicas = read scaling. The exam retests this distinction endlessly.

Practice Q5. An ASG behind an ALB replaces instances only when the VM fails, but sometimes the application hangs
while the instance stays 'healthy'. Fix?

   # Faster instance types -- unrelated to detection.
   # CloudWatch CPU alarm to reboot -- a hung app may show normal CPU.
    Enable ELB health checks on the ASG -- the ALB's HTTP health check sees the app not responding; the ASG then
   terminates and replaces it. EC2 checks watch the VM; ELB checks watch the APP.

Practice Q6. A stateless app runs in one AZ on 6 instances. The architect must make it survive an AZ outage with NO
reduction in capacity and no manual action. What's correct?

   # 6 instances in one AZ with an ASG -- self-healing, but an AZ outage takes all capacity at once.
   # 3+3 across two AZs -- survives, but at 50% capacity until scale-out catches up: 'no reduction' fails.
    Spread MORE than required capacity across AZs so any single-AZ loss still leaves 6 (e.g., 3×3 across three AZs = 9,
   lose one  6; or 6+6 across two). Fault tolerance = pre-paid redundancy; the ALB reroutes instantly.

Practice Q7. When a new object lands in an S3 bucket, three systems must react independently: thumbnail generation
(Lambda), a compliance scan (Lambda), and an audit log (SQS  on-prem puller). Some consumers may be added later.
Best design?

   # Three separate S3 event notifications wired directly -- S3 eventing per prefix/suffix is limited and adding consumers
   means touching bucket config each time.
   # Lambda that calls the other systems synchronously -- tight coupling; one failure blocks the rest.
    S3  SNS topic (or EventBridge)  subscribers (both Lambdas + the SQS queue). Fan-out decouples consumers;
   adding a fourth is just a new subscription. 'Multiple independent reactions to one event'  SNS/EventBridge fan-out.

Practice Q8. A company wants active-passive failover from its primary Region to a static maintenance page when the
primary fails, automatically. Simplest solution?

   # Manual DNS change in an outage -- not automatic; error-prone at 3 AM.
   # Global Accelerator -- fails over between healthy endpoints, but a static S3 page isn't a GA endpoint; heavier than
   needed.
    Route 53 FAILOVER routing: primary record with a health check on the ALB; secondary record aliased to a
   CloudFront/S3 static site. Health check fails  DNS serves the fallback automatically.
